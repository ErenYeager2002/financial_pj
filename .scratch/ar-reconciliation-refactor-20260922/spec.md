# 应收核销执行链重构

Status: proposed

日期：2026-09-22

## 目标

在不改变现有业务判断口径、判定码、金额结果、写前校验、回读校验和日期顺序的前提下，重构应收核销 Skill 的数据传递。每个阶段只接收声明过的输入对象，只生成声明过的输出对象；分支结果、证据和下一步处理统一建模，避免通过共享字典、隐藏字段和“取最新文件”推断状态。

本轮重构的完成标准是：同一组受控材料在新旧执行链中得到相同的判定、挂账原因、写入计划和台账摘要；之后才允许切换线上执行器。真实智云取数、财务工作簿写入和历史失败任务重跑不属于重构验证。

## 当前问题证据

当前新版执行契约有 14 个阶段，后端 `ArExecution` 至少直接调用 19 次外部脚本。`context_json` 同时保存任务控制状态、取数包摘要、工作区路径、计划指纹、写入结果、材料版本和错误状态，已出现 36 类顶层键。业务记录又通过约 78 个下划线字段在付款、订单、SOD、判定和回读模块之间传递。

判定、写前校验、写后复核、挂账重扫和正式台账发布都直接读取 `03_台账` 或 `04_产出` 下的 JSON；阶段之间的接口实际是文件名、目录约定和“取最新文件”，而不是可验证的对象接口。基础工作区、写入暂存区和写后复核区会复制并改写同一批 JSON，导致同一个台账在不同阶段可能代表“历史输入”“本次计划”或“写后证据”。

当前远程工作树还存在其他未提交修改，包含 Skill 恢复、销售缩写和父回款台账调整；本规格不覆盖这些改动，也不把它们当作可丢弃的基线。所有重构切片必须在保留这些修改的前提下实施。

## 目标模型

### 1. 三类状态分开

`RunState` 只记录平台任务控制信息：当前阶段、尝试次数、租约、错误、输入指纹和输出引用。

`ReconciliationState` 只记录本次业务判定所需的只读事实：回款、订单、SOD、交付、结算、材料、流转匹配和经过验证的前序分配。它不写工作簿，也不登记任务完成。

`WriteState` 只记录经过校验的写入操作、实际单元格回读和发布的正式台账包。它不能反向修改判定事实。

历史父回款分配、当前日期的分配计划、跑批进度台账和正式发布包分别建模，不再用一个 `父回款顺序分配台账.json` 在所有阶段兼任四种含义。

### 2. 阶段之间只传 Artifact 引用

所有阶段产物采用统一包络：

```json
{
  "schema_version": "ar-artifact-v1",
  "artifact_type": "decision_plan",
  "workflow_id": "…",
  "batch_id": "…",
  "reconciliation_date": "YYYY-MM-DD",
  "material_set": {"id": "…", "version": 1},
  "skill_hash": "…",
  "inputs": [{"artifact_type": "normalized_receipts", "sha256": "…"}],
  "payload": {},
  "metrics": {},
  "created_at": "…"
}
```

阶段接口只接收 `ArtifactRef` 和少量控制参数；读取器校验类型、任务/批次/日期、材料版本、Skill 哈希和输入指纹。旧的文件名会由兼容适配器转换成包络，业务模块不再自行扫描目录或选择最新文件。

### 3. 所有判断返回同一种分支结果

每个订单或 SOD 的结果统一为 `DecisionItem`：

```json
{
  "case_id": "AR|SO|SOD",
  "status": "write|skip|hold|exception",
  "reason_code": "E2",
  "reason": "…",
  "evidence": [{"source": "zhiyun.order_detail", "ref": "…"}],
  "operations": [],
  "obligations": [],
  "next_action": "…"
}
```

金额、订单号、交付额、流转定位和历史分配不得再通过 `_parent_*`、`_ledger_*`、`_check` 等隐式字段跨模块传递。兼容层可以在入口和出口转换旧格式，但核心规则只读写明确字段。

### 4. 规则按事实与决策分层

判定引擎接收一份不可变 `DecisionInput`，依次调用以下内部规则模块：回款身份与日期、订单来源完整性、父回款金额守恒、订单/SOD 关联、结算与交付、重复核销、前序分配、流转匹配。每个规则返回 `RuleResult`，包含通过、等待、冲突或异常以及证据引用；组合器负责确定最终状态和优先级。规则模块不读文件、不写台账、不改变付款字典。

写入引擎只消费 `ValidatedWritePlan`，分成 `LedgerWriteOp` 和 `FlowWriteOp`。写入、回读和发布各自返回事实报告，不能用“脚本退出码为 0”代替业务成功。

## 分阶段实施

### 第 0 阶段：基线冻结与对照工具

保留当前远程未提交修改，建立重构专用合成夹具和旧链路输出摘要。摘要至少包含每个 `case_id` 的状态、判定码、金额、写入目标和台账摘要。此阶段只增加测试与只读对照，不改变线上执行。

### 第 1 阶段：Artifact 契约和兼容读取器

新增一个深模块 `ar_artifacts`，提供 `write_artifact`、`read_artifact`、`assert_input_binding` 三个外部接口；内部负责包络校验、指纹、任务范围和错误脱敏。为当前判定结果、写入计划、流转计划、执行证据和正式台账包增加兼容适配器。先让现有脚本继续运行，只把边界产物包络化。

验收：旧格式和新包络在同一夹具上产生相同的判定与摘要；篡改日期、材料版本、Skill 哈希或输入文件时均在边界失败。

### 第 2 阶段：只读业务快照和判定引擎

新增 `DecisionInput`、`ReceiptFact`、`OrderFact`、`SodFact`、`DeliveryFact`、`SettlementFact`、`PriorAllocationFact`。由一个读取适配器从取数包、盈亏表、流转表和正式台账构建快照。把 `classification_cli.py` 缩减为参数解析、读取 Artifact、调用判定引擎和写出结果；现有展开模块先作为内部适配器。

验收：所有现有判定码和分支的合成回归通过；同一事实输入不会因为模块调用顺序变化而改变结果；流转匹配仍可独立产生前置结果，不以盈亏写入成功替代匹配成功。

### 第 3 阶段：分离台账和写入计划

建立 `PriorAllocationRepository`、`CurrentAllocationPlan`、`BatchProgress` 和 `FormalLedgerBundle` 四个接口。禁止判定模块直接调用台账的 `load/commit`；写前校验只接收当前计划和经验证的前序事实；正式发布只从写后回读事实生成包。普通跨批次材料仍不能自动变成当前判定依据，同批次前序沿用规则由平台生成的范围凭据控制。

验收：两日链路能够保留同批次前序分配；跨批次相同材料不会带入分配；重复执行保持幂等；发布包与回读摘要一致。

### 第 4 阶段：写入、回读和流转拆成独立事务

`LedgerWriteOp` 和 `FlowWriteOp` 分别生成、执行、回读和报告。每个操作带有原始事实引用、目标单元格引用、期望值和实际值。任何一侧失败只返回可恢复的 `WriteReceipt` 状态，不重新运行判定，也不把另一侧标成完成。

### 第 5 阶段：后端执行上下文收口

新增平台侧 `ExecutionContext` 和阶段清单。`ArExecution` 只负责租约、阶段顺序和 Artifact 引用；路径、JSON 键和 Skill 脚本参数由上下文适配器集中处理。`context_json` 只保留控制元数据和 Artifact 引用，前端继续读取现有状态字段，避免一次重构同时改页面。

### 第 6 阶段：双链路对照、切换和清理

在受控合成材料上运行旧链路与新链路，逐 case 对照；连续通过后再对真实材料做只读影子运行。新链路先只生成计划和报告，保持写入开关关闭；通过人工验收后按 Skill 版本切换。最后删除“取最新文件”、隐式下划线字段和旧兼容入口。

## 必须保留的业务不变量

- 智云核销金额是核销事实来源；流转表负责定位和登记，不替代核销金额。
- 父回款金额、订单/SOD 金额和币种比较继续使用现有已确认口径。
- 缺少订单、结算、交付或历史依据时只能进入明确挂账/异常分支，不猜测、不静默丢单。
- 写入前必须有材料、计划和行坐标指纹；写入后必须回读；正式发布必须与回读事实一致。
- 多日期批次严格按日期升序串行；下一日期只能读取上一日期已发布的工作副本和正式台账。
- 现有 Workflow 与 Pi Harness 共用同一业务计划和写入闸门，重构不产生第二套业务规则。

## 验证矩阵

合成夹具覆盖：无逐 SO 父回款、分笔回款、同 SO 多 SOD、结算回查、交付缺失、重复核销、跨月承接、跨批次材料、同批次前序、流转唯一弱匹配、多命中挂账、空批次、写入失败和回读变化。每个夹具同时保留事实输入、旧链路摘要、新链路摘要和差异原因。

上线前必须通过两份 Skill 源码副本、平台快照、普通版和极速版的契约测试；只做针对性构建和接口健康检查，不执行真实财务写入。新版本部署后回读 API、Worker、Skill 文件和执行版本哈希，保留可用回滚包。

## 第一条实现切片

先做第 1 阶段：新增 Artifact 包络和兼容读取器，接入“判定结果 → 写前校验”这一条边，不碰业务判断和工作簿写入。用三个合成场景证明结果等价后，再扩展到台账和流转链。此切片完成前不删除现有脚本、不改变任务阶段、不调整线上业务规则。
