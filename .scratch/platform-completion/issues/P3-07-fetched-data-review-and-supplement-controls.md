# P3-07 智云取数人工确认与缺失编号补取入口

状态：已完成（2026-08-20）

负责人：前后端联合

阻塞：无；复用现有取数预览、确认和补取接口

## 问题

任务在智云取数后会暂停等待工作人员检查，但当前弹窗把操作区放在长表格下方。员工进入弹窗后看不到明确的继续按钮，也难以发现缺失 AR/SO 编号输入框，无法判断应该如何进入下一环节。源码中已有确认和补取控件，但当前界面可见性、部署一致性和状态反馈尚未达到可用要求。

## 交付

- 取数完成后任务必须停留在“等待工作人员确认取数数据”，未经员工确认不得进入核销判定。
- 弹窗采用固定头部、可滚动数据区和固定操作区；不论表格有多少行，“数据完整，继续处理”和“发现缺失数据”操作始终可见。
- “发现缺失数据”展开 AR、SO 两个输入框，支持空格、换行、中文/英文逗号和分号分隔多个完整编号，并在提交前去重、转大写和校验格式。
- 至少填写一个 AR 或 SO 编号后才允许“按编号补取”；提交时显示处理中状态并防止重复点击。
- 补取完成后刷新汇总、数据表和补取记录，任务再次停留在人工确认阶段；只有员工再次点击“数据完整，继续处理”才进入核销判定。
- 确认按钮提交成功后关闭弹窗、刷新任务步骤，并清楚显示已进入下一环节；失败时保留输入内容并显示可理解的原因。
- 当任务不处于人工确认阶段时，确认和补取接口继续由服务端拒绝，前端不显示可执行控件。
- 核对当前运行服务包含对应前端源码和 API 路由；重建并部署后记录版本或构建时间，避免源码已修改但页面仍运行旧构建。

## 页面布局

```text
智云取数数据（固定标题与核销日期）
├─ 汇总与数据分类
├─ 可滚动的数据表
└─ 固定操作区
   ├─ 发现缺失数据
   │  ├─ 缺失 AR 编号
   │  ├─ 缺失 SO 编号
   │  └─ 按编号补取
   └─ 数据完整，继续处理
```

## 验收证据

- 在 1366×768、1920×1080 和浏览器 125% 缩放下，打开含 50 行数据的弹窗无需滚到底即可看到两个主要操作。
- 员工点击“数据完整，继续处理”后，任务从人工确认阶段进入核销判定，刷新页面后状态一致。
- 输入多个 AR/SO 编号后只发起一次补取；补取成功后新数据可见，任务仍等待再次确认。
- 空输入、非法编号、接口失败和重复点击都有明确反馈，不会意外推进任务。
- 普通员工只能操作本人任务；跨用户、跨部门和错误阶段请求被后端拒绝。
- 前端组件、API 路由、后端确认/补取状态机和生产构建测试通过，并完成一次真实页面角色冒烟。

## 非目标

- 不允许员工在弹窗内修改智云原始数据。
- 不允许补取动作绕过再次人工确认。
- 不把技术堆栈、绝对路径或凭据返回给普通员工。

## 实施结果

- 取数后状态机固定暂停在人工确认阶段；未经确认不会进入核销判定，补取完成后也会再次暂停。
- 弹窗已改为固定头部、独立滚动数据区和固定操作区，并提供“发现缺失数据”“按编号补取”“数据完整，继续处理”。
- AR/SO 输入支持常见分隔符、去重、转大写、格式校验、空输入拦截、处理中防重和错误保留。
- 前端会直接标出错误编号，空输入或存在错误格式时禁用补取按钮；分页末页按完整页边界计算，不会与上一页重复记录。
- 普通员工的确认、补取、错误阶段和跨用户访问均有后端测试；前端组件、BFF 路由、类型检查、契约检查、Lint、生产构建和部署检查通过。
- 新前端产物已部署，生产包中已核对确认按钮和历史版本恢复入口；随后由用户完成 1366×768、1920×1080、125% 缩放及真实员工点击验收。
- 修复 Workflow Worker 只领取 `preparing`、`applying` 阶段动作的问题；`supplementing_fetched_data` 现在复用统一忙碌阶段集合，可以领取已排队的 `supplement_fetched_data` 动作。
- 真实员工从页面提交的补取动作已由 Workflow Worker 自动领取并完成。测试输入的错误 AR 编号被记录为未找到，任务随后回到“等待工作人员再次检查并确认”，没有误进入核销判定。
- 用户已在 1366×768、1920×1080 和浏览器 125% 缩放下完成真实页面验收：两个主要操作无需滚到底即可看到；错误 AR/SO 编号会提示格式错误并禁用补取；有效编号会启用补取，补取后再次暂停。
- 用户点击“数据完整，继续处理”后，任务已进入下一流程；服务端复核显示该任务稳定处于 `awaiting_apply_confirmation`，进度 100%，无排队或运行中动作，刷新后状态一致。
