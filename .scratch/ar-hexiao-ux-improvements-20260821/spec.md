# 应收核销用户体验改进实施规格

Status: ready-for-agent

日期：2026-08-21

## 给实施 AI 的任务

在 `D:\BESTEASY\financial_pj` 中改进应收核销任务的用户体验。开始前完整阅读根目录 `AGENTS.md`、`CONTEXT.md`、`docs/agents/issue-tracker.md`，并检查当前代码与测试。保留现有多日串行处理、一次登录取数、取数人工复核、业务材料版本、安全取消、任务号和长按滑动选日期能力。不要修改应收核销金额判定、Excel 写入、幂等、工作副本、跨日顺序或智云只读规则。

本次只修改开发环境代码和测试，不启动生产端，不部署，不重建或启动生产 Docker。保留工作区中所有无关改动。

## 目标

员工应能快速完成日期选择，看懂当前进度，在智云临时故障后从失败日期继续，并在任务完成后直接看到业务结果。员工页面不得显示脚本名、退出码、服务器路径、请求地址、凭据、客户隐私或重复的技术错误。

## 实施顺序

### 1. 失败信息和原批次重试

修改 `web/src/features/workflow-agent/components/workflow-progress-card.tsx`、`workflow-batch-progress.tsx` 及必要的 API 代理和后端序列化逻辑。

- 单日和批次错误卡片只显示一次业务说明，结构为“哪个日期未完成、发生了什么、员工现在可以做什么”。
- 对 408、429、502、503、504、超时和连接失败等只读取数故障，显示“智云暂时无法访问，本次取数未完成”。不得向员工返回或渲染 `fetch_secure.py`、退出码、异常类、URL、绝对路径和员工姓名重复信息。
- 技术原因保留在受控审计记录中。员工响应只包含安全错误类型、业务说明和可关联的任务号；不要通过前端隐藏来代替服务端脱敏。
- 批次处于 `failed` 且后端允许继续时，显示主操作“重试失败日期”。调用现有 `POST /api/workflow-batches/{batch_id}/retry`，成功后立即刷新批次状态。
- 按钮旁明确说明“此前成功日期不会重复处理”。写入阶段失败或后端返回不可重试时，不显示可执行的重试按钮，展示对应的安全处理说明。
- 防止重复点击；请求期间按钮显示“正在重新执行…”。失败反馈使用 `role="alert"`，成功状态使用非抢焦点的 `aria-live="polite"`。

完成标准：使用 502 取数失败样例时，员工页面没有技术细节和重复字段；可重试批次能从原工作区的失败日期继续，之前成功日期不会重新执行。

### 2. 日期范围选择

修改 `workflow-launcher.tsx`、`workflow-date-selection.ts` 和相关测试。在现有日历上方增加“开始日期”和“结束日期”，作为连续多日任务的主要入口；保留日历单击和长按滑动，用于查看与微调。

- 输入起止日期后，自动选中范围内的连续工作日，默认跳过周六、周日，未来日期不可选。
- 实时显示例如“8 个工作日，跳过 2 个周末”，并列出最终提交的完整核销日期。
- 起始日期晚于结束日期、范围为空或存在不允许的断日时，在日期区域内显示错误，不要只在页面顶部报错。
- 单日任务仍可只选择一天；日历与日期输入必须保持双向同步。
- 保留现有后端连续工作日校验，前端便利输入不能削弱服务端检查。

完成标准：选择 2026-08-11 至 2026-08-20 后，页面自动得到范围内全部工作日，明确显示跳过的周末，并按升序提交。

### 3. 对齐写入确认规则

当前应收核销规则是：工作人员确认智云取数完整后，系统继续判定、校验和生成《核销日清》；日清与写前校验通过后直接写工作副本。只有用户明确选择“只出清单/不要写表”时才停止写入。

- 移除普通应收核销任务的第二次“确认写入”停顿，避免进入 `awaiting_apply_confirmation` 后长期无人处理。
- 保留智云取数完整性确认，这是核销判定前唯一的人工检查点。
- 如果平台还没有“只出清单”参数，不要在本次自行扩展新业务模式；保持现有请求兼容，并记录为后续事项。
- 继续遵守写入安全边界：写前校验失败、指纹变化、材料缺失或业务规则无法安全判断时必须停止；不得自动绕过校验。
- 更新流程状态、批次推进、提示文字及相应前后端测试，确保单日和多日任务都不会等待第二次确认。

完成标准：取数确认后，正常任务自动完成判定、日清、写入和回读；写前校验失败仍停止且没有任何不安全写入。

### 4. 员工可读的进度层级

保留后端细粒度步骤，但把员工端流程归并为五段：准备材料、智云取数、数据检查、核销处理、完成。

- 当前阶段必须同时有文字、图标和状态，不能只依赖颜色。
- 多日批次继续逐日显示状态，突出“当前执行日期”和“当前查看日期”。等待中的日期写明“等待前一日期完成”。
- 细粒度步骤放入可展开详情，默认不要横向铺满 14 个节点。
- 任务刷新或重新进入页面后，保留当前日期和正确进度，不跳回无关日期。

完成标准：员工无需理解脚本步骤，也能判断正在处理哪一天、已经完成多少天、是否需要本人操作。

### 5. 取数复核和完成结果

在 `workflow-fetched-data-dialog.tsx` 中保留四类原始数据分页表，同时增加每个核销日的业务摘要：回款记录数、关联订单数、核销明细数、订单明细数、AR 覆盖率、AR/SO 覆盖率和异常数。后端没有某项可靠数据时显示“未提供”，不得推测。

- 0 笔是合法结果，显示“当天没有核销记录，可以继续”，不要只显示空表。
- 补取历史不要直接向员工展示原始 JSON；改成日期、补取编号数量、结果和时间的可读列表。
- 完成页优先展示处理日期范围、成功写入、已存在跳过、挂账、冲突、流转自动写和需手填数量。数据不存在时不显示伪造的 0。
- 《核销日清》作为主下载操作；变更清单、订单写入差异和工作副本放在次级文件区。文件权限和下载接口保持不变。

完成标准：员工先看到业务结果和待办，再决定是否打开 Excel；所有数字都来自任务真实产出或后端结构化摘要。
