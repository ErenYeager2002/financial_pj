## 1. 目标与完成定义

以本次取得的有效智云明细确定核销事实，以当前选用工作簿确定已经登记的事实。相同业务数据不应仅因历史登记标识缺失、部分存在或来自不同运行而改变核销结论。

最终必须同时满足：

1. 已填记录不重复写，不再次扣减预收。
2. 当前表确实缺失且来源与归属可确认的记录，生成补写计划。
3. 同组部分已填、部分未填时，只补缺失部分。
4. 不覆盖无关回款，不将后续日期回款计入早期核销，不破坏未收余额、计提或结账状态。
5. 真正无法区分的记录给出具体候选、金额、日期和缺失证据；不得只报“历史归属不明”。
6. 首次判定、写前校验、实际写入及写后复核使用同一业务核验契约。
7. 普通版与极速版在相同输入上的业务结果一致。

“当前表为准”不表示当前表中的所有内容都正确，也不表示只凭金额合计相等即可跳过。当前表是已经登记情况的依据，智云有效明细、交付额和用户确认规则仍用于判断应有业务事实。

## 3. 现行链路及冲突点

现行主链路：

`classification_cli 加载旧台账 → classify_one 逐笔身份判断 → 已有回款纠正/基线判断 → 整单结账判断 → 普通定位和拆行 → current_receipt_group 整组补判 → 拆行链组合 → source_history_gap → SO计提闸 → 身份登记 → validate_plan → 写入 → 写后重判`

| 文件/函数 | 已观察行为 | 风险 |
|---|---|---|
| classification_cli.main | FAL.load 后将 baseline_receipts 注入 LedgerIndex | 换表后旧登记影响当前判断 |
| ordinary_receipt_identity.assess | 按 owned、missing、new、legacy、ambiguous 等分支处理；chronological 与单笔 cumulative 比较 | 同组后续已收额会使前几笔误判；登记有无改变路径 |
| classification_decision.classify_one | 未整单结账时 ambiguous 可直接挂账，conflict 也拦截 | 在整组信息介入前形成结论 |
| current_receipt_group.build_partial_existing | 要求 scope_only 台账、排除当前已登记事件，未来回款需台账签名证明 | 当前整组可对应仍不能跳过 |
| receipt_history.plan / receipt_correction.candidate | 根据历史归属、基线台账决定纠正或补写 | 只改首次判断会造成后续分支不一致 |
| baseline_receipts.candidate | 交付变化及部分表格结构进入基线保留模式，台账也参与模式选择 | 清空所有台账可能改变应收拆分方式 |
| source_history_gap.apply / unsafe_write | 来源已结清但材料缺前序金额时转为不补写 | 完整明细可恢复与只有累计值必须区分 |
| classification_accrual._planned_settled_sods | 已保护 ordinary_receipt_proof，其他形态还可能按行已结账推断 | 新增证明类型必须明确是否改变整组结账状态 |
| validate_plan.check_one | 按证明类型分派给多个核验器 | 分类放行而校验仍按旧规则会再失败 |
| verify_execution_write / ar_execution_runner.verify_reconciliation | 先物理回读，再准备复核台账并重判 | 必须隔离本次证据与旧任务记忆 |

计提边界：现有部分整组识别限单 SOD，而多 SOD 计提闸会跳过单 SOD；不能把潜在扩展风险宣称为本次已经发生的计提错误。

## 4. 目标设计

### 4.1 三类数据分离

- 当前来源事实：有效核销事件、金额/币种、到账和核销日期、订单交付与 SOD 关系；标明实际取数覆盖范围。
- 当前工作簿事实：当前材料版本、年度、工作簿哈希、订单所有业务行和已有回款。行号只是本次快照定位信息，不是永久业务身份。
- 执行证据：本次计划及写入回读结果，用于证明本次到底做了什么。旧任务记录保留审计，不作为普通回款已填/未填的单独决定条件。

同日、本次读取的智云有效历史明细与“平台上次运行记忆”不是一回事。跨日累计可使用前者，但必须验证日期、撤销状态、记录完整性和去重，不能假定只取一天就包含订单所有回款。

### 4.2 单一整组核验模块

建议新增 `current_workbook_receipts.py`，作为无文件写入、无数据库读写的纯核验模块。名称为拟定，实施时可按现有模块边界调整。

输入：当前来源事件集合、当前 SO/SOD 行集合、交付额与币种规则、来源覆盖声明、本次计划证据（仅写后复核可选）。普通回款主判定不读旧 journal。

输出契约建议包含：

- policy_version、来源指纹、材料指纹、年度与 SO/SOD 范围；
- 每笔事件状态：already_present、missing、needs_correction、ambiguous、invalid；
- 每笔候选行和实际绑定、匹配依据、字段差异；
- 已匹配行占用情况，禁止同一行被两笔不同事件重复使用；
- 已收合计、本期对应额、后续回款、剩余未收及守恒差异；
- 明确的建议动作：skip、补写候选、纠正候选、待核，不直接执行财务修改。

相同金额/日期事件采用数量与多重集合核验，不能用字典覆盖重复金额。仅当互换不会改变任何业务字段、余额或归属要求时，才可按等价数量处理；否则保留具体歧义，不按行顺序猜 AR。

### 4.3 分组和匹配顺序

1. 验证日期范围、作废、金额/币种、父回款守恒等前置事实。
2. 按业务交付年度路由材料，不按 SO 编号猜年份。
3. 在当前表定位 SO/SOD，禁止跨 SO 借用相同 SOD 或金额行。
4. 先建立组内所有事件和已有回款的候选关系，再统一分配绑定，不能逐笔提前占用并下最终结论。
5. 区分当前核销对应记录、已确认前序记录、后续日期记录。无法验证覆盖完整性时，不因差额自动制造缺失回款。
6. 对已填写完整的记录输出 skip；对缺失记录交给原拆行规划器；对日期/方式差异交给受控纠正规划器。
7. 完成计划后根据整组实际余额决定结账和计提，不能依据单行“是”替代整组结清。

未来回款不能仅因没有 journal 就报错，也不能只看到较晚的日期就认定归属正确；需要当前来源或明确的表内结构证据。证据不足时保护该行并说明影响范围，不拿它补早期缺口。

## 5. 实施阶段与逐文件修改

### 阶段 A：有明确逐笔金额的普通回款

1. 为真实八笔案例建立匿名化最小夹具和只读整链路回放入口，先固定现行错误结果。
2. 新增统一整组核验模块，先覆盖明确人民币、单 SOD、逐笔明细完整的当前案例。
3. `classification_runner.py`：在身份/SOD解析完成后、逐笔最终分类前构建组级证据；所有后续分支读取同一结果。
4. `classification_decision.py`、`ordinary_receipt_identity.py`：新策略下不因历史标识冲突或单笔累计小于表内整组金额直接挂账；保留作废、来源不完整、真正重复和目标歧义校验。
5. `current_receipt_group.py`：分离“已有记录识别（只读）”和旧 build 的“纠正并写入”能力。不能因为匹配到已有行就自动改日期、计提。废除新策略中的“部分已有标识即退出”。
6. `receipt_history.py`、`receipt_correction.py`：新策略复用组级绑定，只对确认的同笔字段差异提出纠正；缺失记录由当前余额生成补写，保留后续回款。
7. `classification_accrual.py`：skip 证明不增加 planned_settled；新动作必须按完整预期行集合计算结清，保留未结清兄弟行。
8. `validate_plan.py`：按新 policy_version 调用同一核验器；重建证明并验证计划字段，只读证明禁止夹带计提、拆行或额外写入。
9. `verify_execution_write.py`、`backend/app/ar_execution_runner.py`：保留工作簿物理回读与保护检查；复核仅注入当前已校验计划证据，不将它混成旧任务登记依赖。
10. `classification_cli.py`：显式标识新普通回款策略；旧台账为其他尚未迁移路径提供兼容，不能在阶段 A 宣称全工具已移除历史依赖。

### 阶段 B：复杂普通回款覆盖

在 A 验收后逐类扩展：跨日来源、等额多笔、分散到多行、多个 SOD、交付额变更、已有计提、外币和尾差。每类必须有真实或业务可解释的反例，无法证明的组合明确报告未支持范围，不能静默回退旧身份规则后宣称“当前表策略”。

`baseline_receipts.py` 的基线保留必须由当前表结构和交付事实确定，新策略不能由旧 journal 存在与否选模式。不可为使总额相等而重写历史应收。

### 阶段 C：父回款无逐笔金额及材料缺前序登记

- `fallback_allocation_ledger.py`、`current_parent_allocation.py`：将当前表已收归属重建与新父回款余额分配分开；无法重建归属时不得重新分配父总额。
- `source_history_gap.py`：分开“缺失明细完整可恢复”和“只有累计、无法逐笔恢复”。前者生成明确缺失集合，后者列出缺口，不把累计数直接作为一笔回款补入。
- 涉及非本次所选日期的缺失回款时，仅报告补跑日期或纳入明确授权的按日任务，不越过本次日期范围写历史日期。
- 后端正式台账服务、材料初始化/台账传递路径需做调用点审计；改为归档审计与本次执行证据分离。未完成这一步不能宣称历史记录完全不影响新批次。

阶段 C 未验收前，不删除旧父回款审计资料或财务安全检查。

## 6. 不应顺带改变的业务规则

- 盈亏核算仍按用户确认的总到账金额口径。2026-09-29用户明确更新：到账流转定位按渠道选金额，微信/支付宝使用智云明确总到账金额（含手续费或税费），其他渠道使用净到账金额；有具体核销明细使用具体核销金额，不自行按交付额、税率或费用比例推算。外币按同一原币比较，按流转表实际汇率处理，不能拿不同汇率本币直接硬比。此确认不授权按1.06换算，也不等于已确认旧表金额差异的修正或多SO费用分摊方式。
- 交付额与应收不同时，保留既有交付额主导规则；不得把本次识别改造变成强制两者相等。
- 流转表的当前有效 SO 核销扣减独立于盈亏是否成功登记；同一来源跨 SOD 仅扣一次。
- 同月续写、跨月冲预收拆行、完整文字预收算式、销售代称、部分更新及未核销标红保持既定规则。
- 缺年度材料继续明确报告，不能写进错误年度。
- 来源作废、币种缺依据、非唯一归属、真正金额不守恒仍须拦截或列异常。
- 不改变失败恢复、材料版本锁、先副本后发布、写后回读和日期串行规则。

## 8. 验证方法及证据产物

1. 静态检查：逐文件差异审查，检查新策略没有 AR/SO 特判、没有削弱作废/完整性/金额守恒检查，保留无关会话差异。
2. 纯函数针对性测试：组内绑定、重复次数、日期区分、余额与计提状态；验证输入不被修改。
3. 变形测试：相同业务表仅改变登记标识或物理行顺序，重建后的业务结论一致。相同工作簿名不等同相同内容，以哈希为准。
4. 真实材料只读分类：固定真实来源和材料指纹，比较修复前后逐笔动作与原因，不直接重跑线上财务任务。
5. 完整写入链验证：对明确隔离、可销毁的财务工作副本执行分类→计划→校验→写入→回读→复核→再次分类，不写正式材料。若需要真实财务数据写入或重跑，按实际用户授权执行。
6. 工作簿对比：检查金额/预收/计提、原公式文字、样式富文本、未相关工作表及行；不能只看测试退出码或JSON统计。
7. 对照真实八月报告：29条缺年度不应因本改造消失；7条应从误挂账变为已登记跳过，而不是强写或隐藏。

诊断脚本、临时导出、对比报告保存在本地 `.scratch`。必须在远程生成的临时产物，取回本地、核对清单和SHA-256后清理远程临时副本。正式业务数据、持久化源码和回滚文件不得清理。

证据包记录：来源/材料/技能哈希、版本、测试命令和结果、逐笔前后结论、单元格差异、未覆盖范围、执行人及时间。业务数据脱敏，不提交凭据或完整财务材料。

## 9. 发布与回滚

- 每个阶段设置明确支持范围；以最终验收结果决定是否发布，不因测试数量多就替代业务验收。
- 发布前重新检查源码已有差异、当前镜像、两个工具的版本与活动任务；与其他会话发布合并，不覆盖对方改动。
- 只暂停受影响工具新任务，等待现有财务任务结束；不启用全站维护，不中断或自动重跑任务。
- 保留当前可用镜像、配置及证明格式兼容回滚。若已产生新格式正式材料/证据，回滚版本须能读取并拒绝不支持的旧计划，不能假定简单降级即可安全恢复。
- 发布后核对API、相关Worker内文件哈希与版本，健康检查和只读功能检查通过后恢复工具。
- 旧失败任务使用固定技能快照，不通过覆盖快照强迫其恢复；按已有恢复/封存入口处理。新版本验收任务是否执行真实核销另按授权。
- 实际发布失败恢复可用服务，并明确未生效范围，不声称已修复。
