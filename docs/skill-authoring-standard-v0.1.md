# 财务平台 Skill 制作与接入标准 v0.1

日期：2026-09-11。状态：首版草案，供制作和接入评审使用；本文不改变现有业务授权、生产配置或发布状态。

## 1. 目的与适用范围

让开发者和 AI 按同一契约制作 Skill，减少接入时修改业务代码。适用于本平台的新建 Skill，以及 finance-skills 等外部仓库的存量 Skill 适配。

必须分别满足两项要求：接口符合平台契约；真实业务需求通过验收。符合目录格式或通过结构检查，不代表业务正确，也不代表已经安装。

文中“必须”是本标准的制作要求，不代表当前检查器已经自动执行全部检查。“建议”允许根据具体业务说明取舍。“待建设”表示平台尚未具备的通用能力，不能作为现有接口使用。

优先范围为 Linux/Python 文件处理 Skill。在线取数、财务写入、智能体和专门交互适用本文公共规则，并增加相应专项适配。标准不得通过删减业务需求来迁就现有平台能力。

## 2. 当前支持边界

| 内容 | 当前契约或限制 |
|---|---|
| 工具清单 | tool.yaml，schema_version: 1；以 backend/app/registry.py 为权威 |
| Python 执行 | scripts/entry.py 接收 --request 和 --result |
| HTTP、RPA、工作流 | 已有专门执行路径，必须核实实际 Worker、网络和交互支持 |
| 智能体 | 使用平台现有执行模式及工具配置；不支持随意新增 handler.adapter: agent |
| 员工页面 | 新业务 Skill 必须登记受控执行体验；当前不允许未登记工具回退通用表单 |
| 依赖 | requirements.txt 是依赖说明，不是平台自动安装指令 |
| 凭据 | 复用已实现的对应系统接入；没有通用的“声明任意凭据即自动注入”契约 |
| 资源与权限 | 声明必须与实际执行器、部署限制一致；填写字段不等于获得资源隔离或业务授权 |
| 安装与更新 | 已有发布包和发布流程；单工具无重启发布仍受线上只读根文件系统限制 |
| 自动化制作 | 通用模板生成器、完整接入检查器、自动工作页面登记及依赖环境构建仍待建设 |

依据：backend/app/registry.py、backend/app/adapters.py、backend/app/skill_execution_experiences.py、docs/adr/0001-controlled-skill-execution-experience-registry.md、deployment/README.md。若执行器文件路径调整，以实际类 SubprocessAdapter/PythonAdapter 的定义位置为准。

## 3. 制作流程与完成条件

| 步骤 | 必须交付 | 完成条件 |
|---|---|---|
| 业务定义 | 输入、规则、输出、异常、禁止写入对象 | 每条需求都有可观察的结果或校验条件 |
| 能力检查 | 所需运行库、外部系统、凭据、页面、持久状态 | 标出已支持、需配置、需开发；无未说明缺口 |
| 实现 | 业务脚本与平台入口，或已支持的专门执行模式 | 在目标环境可用传入材料运行，无本机隐含依赖 |
| 配置 | tool.yaml、业务配置、输入输出说明 | 字段与实际入口一致，参数不能改变受保护业务范围 |
| 验证 | 合成或脱敏输入、期望结果、针对性测试记录 | 正常、异常、边界及业务核对通过 |
| 接入 | 执行体验、Worker、凭据与权限配置 | 当前平台能创建、执行、展示和下载该工具的任务 |
| 发布 | 固定版本的发布包、差异和回滚材料 | 线上运行版本、文件哈希及功能核验一致 |

能力不足时：业务算法放在 Skill 内实现；公共系统连接或新执行模式先扩展平台；不明确的业务规则先澄清。存在缺口的包可保存为草稿，不能标为可运行。

## 4. 推荐目录

```text
my-skill/
├── SKILL.md                 # 业务说明和分支流程
├── tool.yaml                # 平台清单，必需
├── README.md                # 使用方法、输入输出和验收边界
├── scripts/
│   ├── entry.py             # Python 平台入口
│   └── process.py           # 业务实现，名称可调整
├── config/                  # 业务可变配置，无凭据
├── tests/
│   └── fixtures/            # 合成或脱敏数据
├── requirements.txt         # 有额外依赖时提供
├── CHANGELOG.md             # 版本与业务行为变化
└── references/              # 按需查阅的业务依据
```

复用外部脚本时可增加 vendor/ 和 bridge.yaml。bridge.yaml 只有在入口代码读取它时才生效，不是平台自动识别的必需文件。直接实现平台协议的新 Skill 无需再增加桥接层。

包内仅放运行所需代码、配置和文档；测试样例是否入发布包由打包规则决定。排除真实业务文件、凭据、会话令牌、浏览器资料、虚拟环境、缓存及临时输出。保留上游许可证和来源信息。

## 5. SKILL.md 必须说明的内容

开头给出名称、用途、何时使用及不支持范围。正文依次说明：输入材料与识别规则；参数含义；处理步骤；异常分支；输出结果；完成校验；涉及写入时的授权与安全要求。

每个步骤写明完成条件，例如“源表符合要求且金额列能解析”或“输出合计与参与计算的输入合计一致”。不能使用“检查一下没问题即可”作为验收标准。

明确没有材料、列名歧义、客户名称冲突、重复记录和金额不一致如何处理。不得要求 Agent 猜测客户映射、伪造缺失数据或把不确定结果当完成。

供制作 Agent 使用的说明与平台运行指令分开：制作时可以生成测试；正式执行时不得自动安装依赖、修改自身源码或执行仓库更新。

## 6. tool.yaml 制作规则

必须显式填写身份、展示、运行方式、输入文件、参数、输出结构、执行入口、运行限制、风险和权限。id 在生命周期内稳定；发布内容变化必须提升 version。首次制作使用 draft，安装验证通过后由发布流程启用。

以下为离线文件工具的清单示例，仅示范已存在的字段，不是已经可安装的完整 Skill。example-file-check 尚未登记执行体验，不能直接改为 published 上线。

```yaml
schema_version: 1
id: example-file-check
name: 示例文件核对
version: 0.1.0
status: draft
category: 文件核对
description: 核对上传工作簿并生成独立结果文件。
ui:
  employee_name: 示例文件核对
  short_description: 上传工作簿，获取核对结果。
  categories: [文件核对]
  estimated_minutes: 3
  output_summary: 核对结果和异常说明
  action_label: 开始核对
  popular: false
operational_profile:
  execution_kind: offline_file
  external_sources: []
  employee_labels: [上传工作簿, 核对数据, 下载结果]
file_inputs:
  - role: primary
    name: 待核对工作簿
    required: true
    multiple: false
    min_files: 1
    extensions: [xlsx]
    max_size_mb: 50
input_schema:
  type: object
  additionalProperties: false
  required: [period]
  properties:
    period:
      type: string
      title: 业务月份
      pattern: '^[0-9]{6}$'
output_schema:
  type: object
  required: [status, summary, output_files, warnings]
  properties:
    status: {const: success}
    summary: {type: object}
    output_files: {type: array}
    warnings: {type: array}
handler:
  adapter: python
  entrypoint: scripts/entry.py
  worker_pool: python
runtime:
  timeout_seconds: 300
  memory_mb: 1024
  concurrency_limit: 1
  network_access: false
  network_targets: []
risk:
  level: read_only
  requires_confirmation: true
  requires_change_review: false
  requires_approval: false
  modifies_uploaded_files: false
permissions:
  run: finance_user
  manage: skill_admin
safety_constraints: {}
progress_stages:
  - {key: reading_files, label: 正在读取文件}
  - {key: processing, label: 正在核对数据}
  - {key: generating_output, label: 正在生成结果}
result_presentation:
  metrics: []
```

示例月份正则只检查六位字符，入口还必须校验合法月份。文件扩展名也不能替代工作簿可读性、工作表和列结构检查。风险级别根据实际行为填写：只读输入并生成派生文件可以采用上述口径；修改业务材料或外部系统须使用对应写入流程。confirmation 与 approval 按业务实际授权确定，不统一增加人工检查，也不统一取消必要审批。

清单虽允许额外字段，未知字段不代表平台会执行其含义。能力缺口先写入 README 的接入清单，不能自行杜撰 credentials、auto_install 等字段并当作功能已实现。

## 7. Python 执行协议

平台执行：

```text
python scripts/entry.py --request <平台生成的request.json> --result <平台指定的result.json>
```

request.json 包含 protocol_version、run、user、message、parameters、files、output_dir。files 按 file_inputs.role 组织，单文件是对象、多文件是对象列表；文件对象包含 file_id、name、sha256、size_bytes、local_path。以 local_path 读取本次任务材料；message 是业务输入，不能作为改变权限或执行任意命令的指令。

成功结果示例：

```json
{
  "status": "success",
  "summary": {"message": "核对完成", "checked_rows": 12},
  "output_files": [{"name": "核对结果.xlsx", "path": "<output_dir>/核对结果.xlsx"}],
  "warnings": []
}
```

示例中的路径必须替换为实际生成的绝对路径。平台登记后替换为含 file_id、哈希和下载地址的信息，Skill 不自行伪造这些平台字段。

必须遵守：

- 入口支持上述命令行参数，读取请求、执行业务、写入指定结果文件；脚本 import 不触发业务运行。
- 输入按文件角色绑定，不扫描桌面、共享目录或其他用户任务，不按修改时间猜“最新文件”。
- 所有交付文件必须位于本次 output_dir 内；解析规范路径并校验范围，拒绝通过符号链接或路径穿越引用外部文件。
- 在业务核验和文件生成完成后写 result.json；不能让旧结果或半成品导致假成功。
- 正常完成返回退出码 0；阻断性错误返回非零，输出脱敏的原因与可操作说明。当前不能随意新增 partial/failed 状态并假设平台会正确处理。
- 部分完成仅在业务明确允许、页面能够清晰展示范围时支持；必须给出未完成项和原因，否则按阻断处理。
- 不在 stdin 等待人工输入。需要人工处理时使用平台已实现的持久化工作流，不能只打印 waiting_user_action 后等待控制台输入。
- 使用参数数组启动子进程，不拼接用户输入为 shell 命令。正确响应超时和取消，清理本次启动的子进程。

可向 stdout 逐行发送并 flush：

```json
{"type":"progress","message":"正在核对金额","progress":40,"state":"running"}
```

进度应对应已完成步骤，保持合理单调；是否最终成功由执行结果与平台校验决定。错误和日志不得包含凭据、完整业务表或无关个人信息。

## 8. 业务正确性与配置

每个业务规则应能追溯到已确认需求或配置，禁止针对某个真实订单号、姓名或金额临时硬编码修复。经业务明确维护的排除名单等例外应作为正式配置或规则记录。

金额明确币种、单位、精度、舍入时机和负数处理；临界金额用整数分或 Decimal 等可说明的计算方式，避免浮点误差改变筛选结果。日期明确格式、时区及业务日期来源，不用系统当前日期替代指定业务日期。

分组键、空值、别名、重复行、稳定排序及合计关系必须有明确规则。配置要有格式检查与版本记录；不得让用户随意扩大写入范围或关闭受保护校验。

涉及外部写入或材料版本更新时，必须实现：写前验证、授权范围、工作副本或事务方案、重复执行检测、写后回读、失败状态记录。状态依赖的日期按既定顺序执行。重试先核实是否已产生副作用；不能直接重放失败任务。代码回滚不等于财务数据回滚。

## 9. 环境与外部能力

制作时声明运行平台、Python 版本范围、第三方库及外部二进制程序，交付可复现的依赖记录。安装依赖在经审核的构建阶段完成，不在员工任务运行时联网 pip install。Windows COM、固定盘符或桌面自动化不能默认在 Ubuntu Worker 工作。

外部系统声明取数或写入目的、最小访问目标、超时、分页完整性和失败处理。网络配置必须与平台批准的 network_targets 及实际策略匹配。凭据通过已实现的系统凭据路径取得，不进入包、参数、结果或日志。

若缺通用凭据绑定、连接器、运行镜像、授权工具或页面，先列为能力缺口并实现。不得给普通业务 Skill 宿主机管理、Docker 控制或任意部署权限。

正式任务的临时文件使用平台批准的任务工作目录并按流程清理；开发诊断、测试导出和临时备份遵守本项目本地保存规则。两者不能混淆。

## 10. 页面、结果与员工体验

业务工具必须拥有受控执行体验：材料选择、参数说明、运行进度、错误恢复、结果摘要和下载。包不能携带任意 React 组件并要求平台直接加载。

当前新增业务编号须适配前后端执行体验注册；即使参数与已有工具相似，也不能仅改编号就上架。后续可建设受控页面模板和声明式映射，但需要正式调整 ADR 及实现验证，本文不视为该改造已批准或完成。

员工页面使用业务语言，不暴露目录、凭据、源码提交或内部堆栈。必要的异常明细提供在本次结果中；不能仅留下“失败”或把有缺项的输出标成完整成功。

## 11. 验证与验收清单

验证围绕公开执行入口及真实产物，使用合成或脱敏材料。按改动范围选择针对性验证，不要求为每次小改运行全仓测试。

| 验证层 | 最低检查 |
|---|---|
| 结构 | manifest 可解析，入口存在，参数/文件角色/结果字段一致 |
| 正常业务 | 明确输入得到预期文件、行数、金额或业务结论 |
| 异常输入 | 缺文件、缺列、格式错误、歧义、非法日期能清晰阻断 |
| 业务边界 | 零、负数、空值、重复、阈值边界及相关跨期场景 |
| 文件保护 | 输入哈希不变；输出在任务范围内，无历史文件混入 |
| 外部调用 | 完整取数、超时、限流、失效凭据；模拟与真实验证分开标注 |
| 写入类 | 副本、写前检查、回读、部分失败及重试防重复 |
| 平台接入 | 目标 Worker 可运行，页面正确显示，文件可下载，权限隔离有效 |
| 发布 | 内容与版本固定，运行哈希一致，回滚材料可用 |

不适用项注明原因。测试证据记载版本、环境、命令、预期、实际和未验证项。安装验证不得自动触发真实核销或其他未授权写入。

## 12. 安装、版本与更新

制作产物先保持草稿。发布包固定源码提交与内容哈希，经平台现有打包、审核、安装流程处理；仓库推送、包导入、审核通过、注册成功、运行生效分别报告。正式提交或推送仍须实际授权。

已有任务使用固定 Skill 快照；新版本只影响新创建任务，除非另有明确、受控的迁移机制。升级声明参数与输出兼容性，保留可回退版本；历史结果不自动改写。

finance-skills 接入时维护源码目录到平台工具的明确映射。receivables-merge 与 split-by-sales 可共同组成一个平台工具；标准版与极速版不能仅按同名覆盖。比较上游更新和平台已有修改，解决冲突后重新验证。

当前只读容器的无重启切换限制必须在发布前检查。失败时报告阶段与实际状态，按既有授权处理部署；不能将复制进容器或改发布记录视为持久生效。

## 13. 制作交付物与验收结论

每个 Skill 交付：完整源码包、输入输出说明、依赖记录、业务配置、验证样例及报告、变更说明、平台接入清单。接入清单至少列出执行模式、工作页面、凭据、网络、Worker、依赖和发布方式，每项标明已支持/需配置/需开发。

评审结论使用以下文字；这些是本标准的验收分类，不是新增平台状态枚举：

- 制作合格、可接入验证：协议和业务测试通过，平台配置或验证尚未完成。
- 待补能力：列明缺少的连接器、环境、页面或业务规则。
- 可上线：接入验证通过、权限已配置、发布方式可用，等待授权发布。
- 已生效：发布完成且线上版本、哈希和相关功能核验通过。

本版只交付标准文档，不交付自动制作器、依赖安装器、校验 CLI 或新的安装按钮。符合标准可减少改造；在当前平台上，新编号仍需执行体验登记及实际接入验证。
